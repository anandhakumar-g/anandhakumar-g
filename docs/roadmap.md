# Single Point — Phased MVP Roadmap

Reprioritised for market reach and early revenue: the vendor marketplace / offers side moves
ahead of deeper ticketing polish, since that is where reach and initial profit come from.
Foundation still comes first. **Each MVP is built, released, and verified before the next set
is planned.**

| MVP | Theme | Contents |
|---|---|---|
| **MVP-1** | **Foundation** ✅ *shipped* | Resident onboarding (OTP + tenant/flat join via invite code or admin approval), raise ticket (photo + service location), admin view/resolve/assign/reroute, provider accept/update status, push notifications (outbox), single seeded global category list, manual provider verification, immutable status history, multi-tenant isolation (RLS + RBAC), token-based theming (Light/Dark/accent + tenant branding), entitlements seam. **No payment.** |
| **MVP-2** | **Vendor Marketplace & Offers** ✅ *shipped* | Vendor taxonomy expansion (food & dining, retail, travel, accommodation, events & entertainment), provider KYC upload + verification workflow (VERIFIED now gated on accepted docs), Offers/Coupons module with layered targeting, **Super Admin as validating authority for every offer** (incl. enquiry-based targeting off `request_type = ENQUIRY`), mandatory anti-fatigue controls (opt-in category subscriptions, central weekly frequency cap, digest mode, independent ticket/promo opt-outs), custom typography (Bricolage Grotesque + Plus Jakarta Sans) + deals feed. Dedicated React admin console **deferred** — admin/super-admin work lives in the Expo app (also runs on web). |
| **MVP-3** | **Payments (+ taxonomy admin)** ✅ *shipped* | Cash-with-OTP confirmation (resident or provider submits the OTP) + online payment via a `PaymentGateway` abstraction (local stub + Razorpay cloud adapter) + immutable digital receipts with a shareable text. Payments are a loosely-coupled module that never touches the ticket state machine. **Pulled forward from MVP-7:** Super Admin vendor-taxonomy management — verticals ("kinds") are now a lookup table, with CRUD endpoints and a "Taxonomy" screen in the super-admin app; new categories need no migration. |
| **MVP-4** | **Monetization on** ✅ *shipped* | Subscription plans for **communities and vendors** (`com.singlepoint.billing`), lazy FREE default plan so nothing that worked before breaks; `EntitlementService` flipped from a no-op seam to real enforcement — per-calendar-month quotas (`TICKETS_PER_MONTH` / `ADMIN_SEATS` / `OFFERS_PER_MONTH` / `DIRECTORY_LISTING`) return `402 SP-402-QUOTA`, and a lapsed paid plan goes **read-only** (`402 SP-402-SUBSCRIPTION`) after a 7-day grace window — reads always keep working, core ticketing is never metered. Per-period invoices paid through the existing `PaymentGateway` (one-off pay link; Super Admin can also `comp` / `mark-paid`); `BillingRenewalJob` handles period roll → `PAST_DUE` → grace → `EXPIRED`. Manual Super-Admin **Featured vendor tier** (`service_provider.tier`) floats a vendor to the top of the directory + offers feed. Super Admin "Billing" tab + Admin/Provider plan cards (usage bars, pay, self-upgrade). *Deferred: recurring auto-charge, proration, dunning, per-resident plans.* |
| **MVP-5** | **Ticketing depth** ✅ *shipped* | Resident **approval-of-allocation gate** — tenant-configurable, an assigned ticket parks in `PENDING_RESIDENT_APPROVAL` and the provider is engaged only after the resident approves (or declines with a reason). **SLA tracking + breach alerts** — `SlaBreachJob` flags an overdue open ticket once and alerts admins + provider (alert-and-flag only). **Reroute / audit polish** — reroute, provider decline and `ON_HOLD` require a reason; the timeline shows actor names. **Provider ratings aggregation** — `service_provider.rating_avg` / `rating_count`, recomputed on close, sortable in the picker. **Ticket-category admin** — Super Admin owns the global catalogue + any community's list; a community self-manages when `tenant.category_admin = COMMUNITY`. **WhatsApp channel** — additive delivery for ticket notifications, gated by the `WHATSAPP_NOTIFICATIONS` plan entitlement + a per-user opt-in; profile-split sender (log / Meta Cloud API). **Provider directory management + availability** — admin edit / per-community deactivate-restore, provider self-service profile + `AVAILABLE/BUSY/AWAY` (advisory), resident `away_until`. **PII hardening** — ticket free-text + addresses encrypted at rest (`PiiBackfillRunner` for legacy rows), service address masked for non-parties, `@AuditRead` on contact/location reads. *Deferred: name-at-rest encryption, multi-key rotation impl, WhatsApp for promos, allocation-approval timeout, SLA auto-escalation.* |
| **MVP-6** | **Reach expansion** ✅ *shipped* | **Switch-community** — `POST /me/active-community` re-mints a token scoped to another of the resident's communities; `POST /auth/refresh` (fixes the approved-resident stale-token gap); `POST /me/memberships/{t}/leave` (EXITs + flat unlink + fallback). **Direct-to-Provider** — `tenant.direct_service_enabled` (Super Admin + community admin); contact-free `GET /providers`; `POST /tickets` with `providerId` → `request_mode = DIRECT_SERVICE`, straight to `ASSIGNED`; on a provider decline the resident re-picks (`POST /tickets/{id}/rebook`). **Household model** — a `user_tenant_membership` is now user↔flat; `household_role` PRIMARY/SECONDARY; a PRIMARY issues `HOUSEHOLD` invite codes (family joins as SECONDARY, no admin step); one user can hold flats in several communities or several flats in one; **`flatId` is required on raise** once you're in a flat, and every query/feedback/request names its flat. *Deferred to MVP-7: community-less individual service users, multi-community admins, Super-Admin-gated provider onboarding, admin/provider raising a ticket as a flat owner.* |
| **MVP-7** | Actor-model expansion | Community-less **individual service users** (onboard with no community, book a provider directly — needs tenant-less service requests / RLS work); **admins mapped to one or more communities** with a switcher; **provider onboarding gated to the Super Admin** (admins add only with permission); any role (admin / provider) that is also a flat owner can **raise a request for their own flat**. |
| **MVP-8** | Platform scale | Multi-tenant self-onboarding, full Super Admin console, analytics dashboards. *(Vendor-taxonomy self-service governance pulled forward to MVP-3.)* |

Data-model columns and service seams for later MVPs are pre-placed in MVP-1 where doing so
avoids a migration later (`request_mode`, `sla_due_at`, `flat.owner_user_id`, `tier`,
`EntitlementService`, `vendor_category` taxonomy table, `PushSender` interface).
